# Knowledge Manager 1.0 Phase 2 Proposed Implementation Authorization

**Status:** Proposed

**Date:** 2026-08-05

**Decision owner:** Chief Architect

**Required prior evidence:** Independent Work Mode exact-head review

## Proposed disposition

**A. AUTHORIZE PHASE 2 SYNTHETIC IMPLEMENTATION**

This is a proposed decision, not an effective authorization. It becomes
effective only if the Chief Architect adopts it for the exact remote activation
package head after independent Work Mode review and the approved package is
merged to canonical `main`.

## Decision basis

The proposed authorization is appropriate because:

- Phase 1 implementation and closeout are canonical;
- the Phase 2 architecture and validation baseline is canonical;
- the implementation objective and file manifest are exact and bounded;
- the candidate is standard-library-only and adds no dependency;
- the threat model covers every required named threat with prevention,
  detection, failure default, sanitized audit evidence, a deterministic test,
  and a canonical owner;
- repository implementation, architecture, independent review, validation,
  synthetic execution, cleanup, evidence, and closeout responsibilities are
  assigned to existing canonical roles;
- future runtime operations and live-information ownership remain explicitly
  unassigned and outside the authorized scope;
- rollback requires no migration, service shutdown, or external cleanup;
- no real document, runtime integration, deployment, or production persistence
  is required; and
- every broader capability is an explicit stop condition.

## Exact authorized scope

Authorize Codex - Implementation Engineer to implement only the exact package,
records, enum values, fields, invariants, interfaces, methods, in-memory
reference adapters, SHA-256 synthetic integrity verifier, transition
enforcement, orchestration, generated fixtures, tests, documentation, and file
manifest in the
[Phase 2 Synthetic Implementation Activation](../KNOWLEDGE_MANAGER_1_PHASE_2_SYNTHETIC_IMPLEMENTATION_ACTIVATION.md).

The implementation may:

- create immutable document-admission and inspection evidence models;
- model quarantine, byte identity, policy, state, retry, cleanup, and audit
  evidence;
- enforce the exact admission and transformation transition graphs;
- define storage-neutral detector, evaluator, inspector, eligibility,
  quarantine, journal, and cleanup interfaces;
- compute SHA-256 only for generated synthetic bytes under
  `synthetic-sha256` version `1`;
- hold generated bytes in per-test process-local in-memory quarantine;
- coordinate injected scripted test doubles;
- use the deliberately small `synthetic-resource-limits` version `1` profile;
- create deterministic synthetic fixtures and tests; and
- update directly affected documentation.

## Explicitly unauthorized

This proposed authorization does not permit:

- real VBA or organizational documents;
- local document discovery, copying, hashing, inspection, parsing, extraction,
  submission, upload, or ingestion;
- a real PDF, DOCX, TXT, or Markdown parser;
- OCR, malware scanning, archive extraction, macro inspection, external fetch,
  subprocess/container isolation, or executable content;
- production source-artifact persistence, a durable quarantine, database,
  migration, backup, restore, or retention service;
- services, APIs, CLIs, queues, schedulers, watchers, user interfaces, Open
  WebUI, n8n, FastAPI, Docker, or deployment;
- Knowledge Registry writes, Memory Service integration, Qdrant, embeddings,
  models, generated summaries, retrieval, indexing, ranking, or promotion;
- dependency or lock-file changes;
- changes to the existing Collector file adapter or runtime composition;
- autonomous admission, human-approval substitution, source correction, factual
  verification, general consumer authorization, or action; or
- implementation outside the exact future manifest.

## Authority and ownership

- Chief Architect: architecture, scope, sprint authorization, exceptions, and
  final merge decisions.
- Codex - Implementation Engineer: bounded implementation, synthetic fixture
  construction, validation execution, cleanup, rollback, and handoff.
- Work Mode: distinct independent architecture/security-quality and
  implementation review.
- Documentation Suite: post-merge canonical closeout.
- Collector Engine component owner: existing **Maintainer accountable** state in
  the Component Registry; this decision creates no new component.
- Jebediah Runtime: no authority, access, or operational responsibility.

No real information owner, source, producer, submitter, consumer, custodian, or
runtime operator is assigned. Those roles are unnecessary for generated
synthetic test values and remain blockers for any real or deployed use.

## Implementation gates

Before coding:

1. The complete activation package exists at one remote exact head.
2. Documentation, links, whitespace, sensitive-value, scope, authority, and
   manifest checks pass.
3. A distinct Work Mode instance returns **APPROVED** with no unresolved
   Blocking, High, or Medium finding.
4. The Chief Architect adopts this decision for that exact head.
5. The reviewed activation package merges to canonical `main`.
6. Codex verifies clean synchronized `main`, records the implementation base,
   runs the existing full test baseline and documentation validation, and
   confirms protected paths and lock files are unchanged.

A changed activation-package head reopens review and authorization.

## Implementation review and merge gates

Implementation must:

1. Remain within the exact source, test, and documentation manifest.
2. Pass all targeted and full-suite validation in the activation package.
3. Prove package, content, network, runtime, dependency, and authority-negative
   boundaries.
4. Publish one clean remote exact implementation head and complete handoff.
5. Receive a fresh, independent Work Mode implementation disposition.
6. Stop for a separate Chief Architect exact-head implementation merge decision.

This authorization does not approve the future implementation merge.

## Rollback

Before implementation merge, abandon or revert the bounded branch. After an
approved merge, revert the bounded implementation through normal review and run
the full validation set. No data migration, service shutdown, credential
rotation, external cleanup, or real-information correction applies.

## Stop conditions

Codex stops and requests revised architecture and authorization if:

- any real or external document is required;
- a parser, scanner, isolation mechanism, dependency, external binary,
  filesystem adapter, network call, service, or durable store is required;
- a protected path or dependency file must change;
- exact models, state semantics, interfaces, authority, ownership, or file scope
  must change;
- a test requires host resource exhaustion, functional malware, executable
  macros, an exploit, or private data; or
- validation, cleanup, or rollback cannot fail closed.

## Real-document boundary

Even a successful, merged synthetic implementation authorizes no real document.
Real VBA material remains outside Jebediah until a separate information-domain,
source, producer, submitter, consumer, classification, privacy, legal,
retention, deletion, operations, persistence, recovery, dependency, threat, and
exact-scope decision is independently reviewed and approved by the Chief
Architect.
