# Knowledge Manager 1.0 Phase 2 Synthetic Threat Model

**Status:** Proposed

**Date:** 2026-08-05

**Scope:** Generated synthetic bytes and metadata processed only by the
disconnected repository candidate defined in the
[Phase 2 Synthetic Implementation Activation](KNOWLEDGE_MANAGER_1_PHASE_2_SYNTHETIC_IMPLEMENTATION_ACTIVATION.md)

## Assets and trust boundaries

Assets in scope:

- immutable synthetic submission and policy metadata;
- process-local generated byte sequences;
- content identity and integrity evidence;
- append-only state, inspection, cleanup, and audit evidence;
- deterministic test results; and
- repository authority and package separation.

Trust boundaries:

1. Synthetic test caller to submission envelope validation.
2. Synthetic payload to process-local quarantine placement.
3. Quarantine to injected detector, evaluator, and inspector interfaces.
4. Interface result to state-transition and policy enforcement.
5. Process-local evidence to sanitized test and review output.
6. Candidate package to protected Collector, registry, memory, runtime, and
   service packages.

No network, real source, production store, service, parser product, or deployed
consumer is in scope.

## Ownership

- Codex - Implementation Engineer owns implementation of prevention, detection,
  sanitized evidence, deterministic tests, cleanup, and rollback.
- Work Mode independently validates architecture, security-quality, and
  implementation evidence.
- The Chief Architect owns risk acceptance, scope exceptions, and authorization.
- The Documentation Suite records accepted post-merge conclusions.
- Jebediah Runtime has no authority or access in this phase.

## Residual risk

The synthetic candidate does not prove:

- that a real parser is safe;
- that an operating-system sandbox enforces isolation;
- that malware can be detected;
- that PDF or DOCX structures are correctly identified;
- that live numeric limits are safe;
- that a durable quarantine can be recovered or deleted;
- that real logs, temporary files, backups, or operators protect sensitive data;
  or
- that a real information domain, source, submitter, consumer, or use is
  authorized.

These are explicit blockers for parser selection, runtime implementation,
deployment, and real-document use.

## Review triggers

Fresh architecture, security, dependency, and owner review is required before:

- adding a parser, scanner, archive/XML library, external binary, subprocess,
  container, filesystem adapter, network call, or durable store;
- accepting a real information classification or source;
- changing state semantics, candidate formats, authority, retention, cleanup, or
  recovery responsibility;
- enabling an ordinary/runtime consumer; or
- changing the exact synthetic scope.
